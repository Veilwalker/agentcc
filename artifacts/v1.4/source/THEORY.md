# 1.4 容量约束下的具体调度编辑

本项目把当前拓扑转成有向链路与共享资源的容量约束，让 LLM 对合法备用路径提出具体分流数量，再把提案编译为可回放的调度。确定性搜索同步产生强对照；模型的完整候选、兼容轮次或原子路径组合通过验证且有收益时，才进入最终结果。

核心设计是“容量模型—有限编辑空间—联合数量决策—验证与组合”。需要分别考察通信性能、完整请求时间、Token 和稳定性，不能只用可行率或某个阶段的改进证明综合收益。没有训练神经调度器，也没有证明长上下文机制本身带来优势。已完成实验及其版本、源码和测量条件以 [VALIDATION.md](VALIDATION.md) 为准；历史平台成绩不能当作当前代码的成绩。

按用户补充的平台说明，自动榜性能分占综合成绩 70%，专家与 Token 消耗评分单独复核、合计占 30%。因此不把 Token 节省折算成自动榜分数，也不把全部 30% 描述为专家主观分；当前没有完整的复核评分公式，不预测综合总分。

## 研究依据与本项目的工作

师兄的 [SmartCCL 论文](materials/research/2026085860-1.txt) 使用学习模块提出转发动作，再集中消除冗余并调整时间步。本项目采用其中的容量建模、候选与集中处理分离的思路，按本赛规则实现 LLM 编辑和精确验收，没有复现其神经网络训练或推理。

[TACCL](https://www.usenix.org/conference/nsdi23/presentation/shah) 通过通信草图，让设计者缩小集合通信合成的搜索空间；[TECCL](https://arxiv.org/abs/2305.13479) 将集合通信调度与多商品流和流量工程联系起来。这些工作支持先建模资源、再搜索受约束动作的研究方向，不直接证明本项目的效果。

本项目具体实现并验证的是：保留实际资源关系的紧凑编辑上下文、模型输出到原子分片的可追溯编译，以及保留程序优化成果的安全组合。容量模型、局部搜索、验证后接受都已有研究基础，不能单独包装为原创理论；本项目的性能贡献以对照和消融为证。

一个联合编辑的动机例子是资源负载 `(10,10,0)`：两个合法动作的增量分别为 `(-2,0,+2)`、`(0,-2,+2)`，单做一个动作最大负载仍是 10，联合执行后为 `(8,8,4)`。这解释了为什么只接受单步严格下降的贪心可能停住，也解释了给模型多个关联动作的必要性。确定性联合搜索同样可能解决它，因此该例不证明 LLM 更优。

## 官方容量与计时规则

依据 [共享资源规范](materials/spec/SHARED_RESOURCES.md) 和 [输出格式](materials/spec/OUTPUT_FORMAT.md)，一轮由若干 Rank 到 Rank 的完整路径传输组成。设每 Rank 数据量为 D，切分数为 S，原子分片大小为 b=D/S。AllGather 的负载为原始分片个数乘 b；AllReduce 的负载为唯一规约槽位数乘 b。包含多个贡献者的完整规约表达式仍是一个槽位的数据。

以下时间用秒，容量用 B/s。对传输 i，实际负载为 q_i，路径为 P_i：

```text
h_i = (startup_us + 中间交换机数 × switch_overhead_us) / 10^6
H   = max_i h_i
B_e = Σ_{i: e 在 P_i 中} q_i
B_r = Σ_i m_ir × q_i
```

m_ir 是路径 P_i 上绑定资源 r 的边数。同一路径经过该资源的两条边，计两份负载。一条边属于多个资源时，每个资源分别计入完整负载，不按资源个数分摊。相同有向节点对重复声明的基础带宽先相加，资源绑定按集合处理。

```text
T_k = max(
    max_i [h_i + q_i × Σ_{e 在 P_i 中} 1/C_e],
    H + max(max_e B_e/C_e, max_r B_r/C_r)
)
T = Σ_k T_k
```

轮长由该式计算。带宽不是每轮固定的字节硬上限，也没有默认的交换机带宽均分。若用固定时长 Δ 检查本轮能否完成，除完整路径时间不超过 Δ，还须满足 B_e≤C_e(Δ−H)、B_r≤C_r(Δ−H)。单独使用 C_eΔ 会遗漏启动开销、完整多跳路径及共享资源限制。

SmartCCL 的文本使用离散时步容量生成动作，随后也调整时步。本项目借鉴提出候选后集中验证的结构，状态与计时始终按 AgentCC 规则处理。论文的 AllGather 和 GPU 推理实验不能直接推断本赛 256 Rank、单 CPU 环境的表现，参见 [论文摘录](materials/research/2026085860-1.txt)。

## 快速基线与等待期间的搜索

[src/service.py](src/service.py) 先生成通过 Replay 的快速初始方案。AllGather 优先用最小合法切分，AllReduce 优先用最大合法切分；异常拓扑仍走构造器的合法首解保护。目录提取完成后发出一次真实模型请求，等待响应期间继续从该初始方案搜索其他合法集合通信方案，并执行不冻结任何模型传输的完整确定性改路流程。

这里的“完整”指执行完该有预算的构造、精修和广泛改路流程，并不表示穷举所有调度或证明全局最优。控制候选可以具有不同切分、节点顺序或数据动作，不能默认与模型候选逐轮兼容。

广泛改路阶段以固定工作量代替正常的墙钟截止：最多约 20,000 次路径评分、65,000 次边松弛，另设 3 秒异常保护。完整传输的候选评分完成后才停止；最短路在一个展开节点后批量计数，因此可能超出上限一个节点的出度。后续传输保留原路径，候选仍经完整 Replay。参数从公开样例的工作量实验选择，对所有拓扑相同，不按实例名分派；它保证相同阶段输入、未触发异常保护时工作量可复现，不保证整个请求耗时恒定。构造与已有路径优化仍有软时间预算。

为避免重复验证同一份未变方案，构造器可以交出刚产生的真实 Replay 报告。服务将报告从策略记录取出，通过显式的 `validated_report` 参数交给提取器。提取器检查有效标志、切分、非空轮数、各轮时间及总和等结构一致性；它不相信方案中的 `metrics`。该接口是内部可信调用约定，不是对任意外部报告的真实性证明。不提供报告的普通调用仍执行完整 Replay。

模型编译器仅在接受候选时交出私有 `_validation_report`，它对应过滤后实际返回的方案。服务取出后用于选择，不把私有报告放进公开编辑证据。被拒绝的原始候选报告不能代替最终返回方案的报告。

## 紧凑输入与具体数量决策

[src/schedule_edit.py](src/schedule_edit.py) 生产提取最多 2 组、1 个可编辑瓶颈轮。生产提取使用 10,000 次候选路径检查、65,000 次边松弛的固定工作量，另设 3 秒异常保护；基线验证、负载初始化和完整字段生成仍需完成。完整传输的备选路径分析结束后再停止，避免正常机器负载变化截出不同分片前缀。这是有限的编辑机会预算，不是全局最优性保证；同轮两组仍需联合分配，未选中轮由独立控制搜索处理。每组成员绑定固定轮次、原传输编号和当前合法的备用路径；成员之间不重叠。同组可以包含多个 src/dst，但每个成员自己的端点、动作和原子数据不变。

模型实际接收的是 [src/llm.py](src/llm.py) 投影后的紧凑数据：

- 全局 `constraints` 表按物理资源或有向边去重，保存容量；各轮 `loads` 和各组 `delta` 共用列序。`loads` 中的 null 表示该列在这一轮未涉及，不表示零负载。
- `delta` 是整个组全部移动时的微秒负载变化。给定模型数量 k，组上限为 M，线性部分按 `delta × k/M` 累加，同轮各组需要联合考虑。
- 所有受影响的共享资源都保留，包括多次经过、重叠绑定和净增量为零的资源。交换机间边的变化显式进入差分；终端边还依赖前缀具体包含哪些成员，另给路径、边负载上界与最小相关边容量。
- `floor` 是不可编辑路径和不受任何候选触及的边、资源负载形成的固定下界，可能较松。`path` 和 `overhead` 是当前值，改路后可以改变；它们不是固定下界。完整 Replay 根据编辑后的实际路径重新计算全部成本。
- 路径样本、原子分片大小、组数量上限和输入绑定标识保留。无可编辑组时仍提供当前拓扑的实际边、容量与共享资源摘要。

提示中的时间单位转换与有限精度表示只用于提出候选。它不是完整拓扑验证器，也不会把终端边效应假定为已精确线性化。接受与否使用未经该投影舍入的实际拓扑和完整 Replay。

1.4 在上述投影之上增加可逆的表格编码：节点和资源名称分别映射为整数，约束与轮次使用数组，约束列按物理标识排序后同步排列负载和增量。编辑组保留 `max_chunks`、`delta` 等字段名，以清楚表达数量语义。原始名称、列排列和组标识保留在 `input_encoding.aliases` 中。方向、容量、全部零增量、null 和组顺序均保留；可以还原 1.3 的投影，但不能据此宣称投影等价于完整拓扑。压缩的目标是减少表示开销，不删除模型决策所需的容量关系，也不代替模型填写数量。探索实验中，全部数组化虽然更短，却出现更保守的数量决策；因此不以字节数最小作为唯一选择标准。

模型按给定组顺序返回数量数组。例如目录实际给出的标识为 `82bd103c45e691af` 时，回复形如：

```json
{"base":"82bd103c45e691af","counts":[12,7]}
```

实际提示嵌入本次真实标识。客户端检查数组长度和整数类型，按固定组序无损解码为 `edits: [["g0",12],["g1",7]]`；编译器再检查绑定、已知组、重复组及数量范围。客户端不补全、不截断、不修剪、不替换数量，也不执行数量优化。原始请求、原始响应、原始数量数组和规范化编辑分别留证。显式 `edits` 格式仍兼容旧响应与回归工具。

一个数量表示按固定成员顺序移动多少个完整原子项。移动在一个 transfer 内结束时，将其拆成两个互不重复的分片集合，分别走备用路径与原路径。AllReduce 的整个贡献表达式是一个原子项，不拆开其中贡献者。模型无权创建任意边、分片、轮次或规约动作。

## 编辑器保持的不变量

在实时输入、初始方案及私有编辑上下文未变的前提下，路径编辑保持：

- 每个 `(round, action, src, dst, 完整原子表达式)` 的出现次数不变。已有数据依赖、重复接收规则与 AllReduce 贡献集合仍由完整 Replay 校验。
- 新路径的端点不变，中间仅含交换机、节点不重复，每一跳都是当前声明的有向边。交换机不跨轮保存数据。
- 切分、初始持有关系、最终要求和非空轮数不变。同轮分包可以增加传输条目，但不增加通信轮次。
- 应用前重新计算实时任务、拓扑语义字段和初始 solution 的摘要。只比较缓存的 `Topology.input_sha256` 不能发现内存中后来发生的容量变化。初始方案摘要不包含 `strategy` 中的诊断计时；实际分片、路径、轮次及 metrics 仍受绑定。模型的 `base` 还绑定实际编辑目录，避免将同一基线上的不同目录误认为同一次提案。

编译器先将整个提案编译并完整 Replay。结构错误、过期绑定或非法联合方案整体拒绝，不能通过删掉某些错误动作补救。对于合法提案，只保留相对初始方案严格改善的整轮，其他整轮恢复初始方案；保留轮内的模型数量和路径不变。存在恢复操作时再次完整 Replay，没有严格改善则返回初始方案。

这使编辑器返回的本地通信成本不劣于其基线，不能据此推出比赛总分不下降。目录提取、模型等待、序列化及验证会消耗请求时间，模型还产生 Token 成本。本地 Replay 的结论以公开规则实现正确为前提，不能替代官方 Judge。

## 与完整控制候选比较

[src/selection.py](src/selection.py) 比较已经完成确定性搜索与改路的控制候选 C、通过编辑器验收的模型候选 F。首先比较两个完整候选的总耗时；即使切分或动作序列不同，也可以选择更快的完整合法方案。

轮次组合另有严格门槛：两者切分、初始持有、最终分片要求及轮次数必须一致。对于模型中已改善的轮次，只有其完整原子动作多重集合与控制候选对应轮完全相同，且该模型轮更快，才允许替换。组合方案再做完整 Replay，并且必须优于当前完整候选赢家才会被选中。

原子集合比较保留动作、端点、完整表达式和重复次数。AllReduce 的一个 `r0_c0+r1_c0` 不等同于两条分别发送 `r0_c0` 和 `r1_c0` 的动作。不同切分、节点排序或算法产生的不同动作序列，不能仅因为轮号相同就混合。

最终选择后不再为保留模型动作追加受限改路。确定性控制已经完成不冻结动作的优化；模型只有整体更快，或在数据动作兼容的轮上提供额外改善，才能进入结果。这保证相对于本次已经算出的控制候选不牺牲通信成本，不保证超过任意其他确定性算法。

1.4 还检查同轮原子路径组合。若 seed、模型与控制轮的完整原子动作多重集合相同，先按 seed→模型提案识别模型实际移动的全部原子项，再把这些项的目标路径完整应用到控制轮，其余项保留控制路径。不会修改模型数量、重新优化其比例或只挑其中几个分片。控制包仅在不同原子项需要不同路径时拆分；已经位于目标路径的原子项不再人为拆包。重复原子身份无法明确对应时，保守跳过该轮。

这允许模型改善一部分瓶颈，同时保留程序对同轮其他部分的改进。按原子项迁移与按整轮替换都不改变轮初、轮末的数据语义。局部成本估计只用于排除无益候选，新组合仍需完整 Replay；失败时保留已验证的原选择结果。`without_overlay_time_us` 记录没有这一步时真实会返回的成本，避免把控制搜索的收益计作原子组合的收益。

额外组合设置 0.1% 的总通信相对收益门槛，达到后才支付新增完整 Replay 的成本。该门槛是实验指导的资源开销政策，不是由未知的官方 `L/U/t_good` 推出的评分最优值；会明确放弃极小的通信收益。旧有整模型或兼容轮次赢家始终保留，门槛不会修剪模型数量或免除最终验证。预测收益、阈值与拒绝原因均留证，便于后续复核这一取舍。

## 为什么允许部分轮次组合

对被替换的轮次，路径和同轮分包的变化保留完整原子动作多重集合。因此，在相同轮初数据状态下，合法执行后得到相同轮末数据状态。以控制候选为基础逐轮归纳：未替换轮原样执行，替换轮执行相同数据动作，所以后续轮的依赖状态保持一致。交换机和资源负载不跨轮保留，轮长可直接相加。最后的完整 Replay 仍是必需验证。

忽略浮点下降容差，编辑器按轮筛选得到的 F 不劣于初始方案 B。设 E 为满足兼容条件且模型轮严格更快的轮集合，组合方案 U 在 E 中使用 F，其余轮使用 C，故 U 的总成本不高于 C。最终在有效的 C、F、U 中选最优完整候选，结果不劣于本次控制候选；F 存在时也不劣于 F。并不要求 C 与 F 的每一轮都兼容，也不声称 U 必然逐分量优于二者。

代码使用严格下降容差，避免将浮点级差异作为改善。若未来允许跨轮移动、改变规约贡献或重建数据依赖，不能直接沿用上述路径编辑的证明。

## 审计字段的含义

`model_edit.accepted` 表示编辑器至少保留一个相对初始方案严格改善的模型轮。`selected` 表示模型候选整体胜出，或有兼容轮/原子路径组合进入最终结果；`combination` 区分 `control`、`whole_model`、`compatible_rounds` 和 `atomic_overlay`。`accepted=true, selected=false` 不代表模型动作最终采用。

`selected_rounds`、`selected_edits` 和 `selected_edit_manifest` 只描述最终采用的模型部分。`selected_transfers` 是这些移动前缀在最终所选轮中的实际传输位置，是观察记录，不是给后续优化器的冻结约束。`preservation_scope="observed_not_enforced"` 与空的 `selected_frozen_transfers` 明确表达这一点。`preserved_in_final` 表示所选模型部分出现在最终方案中，不能解释为固定了模型提议的全部分流比例。

原子组合重新定位最终分包位置，使用 `selected_manifest_format="atomic_paths_v1"`。`selected_atomic_positions` 和清单中的完整表达式标明精确原子范围；某个 `selected_transfers` 包含模型原子项，不代表包中全部分片均由模型改动。清单同时保留 seed 路径、模型目标路径和控制路径，可核验原子来源与实际增量。

`proposal_time_us` 是原始联合提案成本；`after_us/returned_us` 是编辑器按轮恢复后返回的成本；`control_time_us` 是已完成优化的确定性控制成本；`selected_time_us/final_time_us` 是最终选择成本，当前两者相同。原始响应保持原样，不能把按轮过滤或最终选择后的动作列表冒充模型最初的回复。

候选历史中只有一条记录的 `selected` 为真。模型记录的 `parent_candidate` 指向实际生成编辑目录的 seed，`control_candidate` 单独记录被比较的确定性候选。整体模型方案胜出时，其算法与切分来自 seed；兼容轮组合保留控制方案的整体程序记录，并列出采纳的模型编辑。不能把控制候选误写为模型编辑的原始基线，也不能把所有确定性优化收益算作模型贡献。

## 需要怎样的实验结论

公平的数量决策比较必须固定当前输入、初始方案、编辑目录和验证器。[同目录消融工具](tests/edit_ablation.py) 在相同数量空间内进行有预算的确定性搜索，采用同样的整轮恢复规则，最终经过编辑编译器和完整 Replay。它没有最优性证书，也不在生产中伪装模型响应。

应分别报告保留基线、同目录确定性数量搜索、模型编辑阶段和完整服务的有效率、通信耗时、端到端耗时、Token、内存与输出体积。完整控制的动作空间可以更大，因此它适合检查最终服务是否牺牲已有优化能力，不能单凭胜负归因模型的数量决策能力。

判断上下文机制是否带来收益，还需要固定候选目录的上下文消融、重复测量及未见输入测试。带宽、方向、连边、重叠资源和节点命名变化用于检查输入依赖与泛化。模拟模型响应只能验证工程路径，不能证明真实模型能力。当前没有证据支持“LLM 必优于确定性”或“长上下文本身已带来优势”。最新实测结论统一记录在 [VALIDATION.md](VALIDATION.md)。

## 稳定性与不确定性的边界

相同输入得到不同结果至少有三种来源：按墙钟截止的搜索完成了不同工作量；模型面对相同提示返回不同数量；网络、服务端和本地调度改变请求耗时。只有实际输入和提示哈希相同，才能把回复差异当作固定输入下的模型差异。平台实例名称相同不足以证明完整输入相同。

1.4 排除提示绑定中的诊断计时，固定资源列序，具体编辑请求使用 `temperature=0`，保留原始回复并只请求一次。零温度降低采样随机性，不保证服务端绝对确定；没有使用未经验证的 seed 参数，没有为获得好答案反复采样，也没有缓存固定实例答案。模型建议仍要通过约束与收益检验，因此随机提案不能使最终本地通信成本比本次控制候选更差。

目录提取与广泛改路都用固定工作量作为正常停止条件，实际消耗和停止原因分别记录在 `search.edit_extraction_work` 与 `search.route_finish.work`。这不等于跨请求逐位相同：控制候选的构造和已有路径优化仍可能受搜索截止影响，服务端延迟也不能由本地代码消除。实验证据需分别报告固定提示的模型重复、固定模型回复的程序重复和完整 SDK 重复，不能把三者混为一项“稳定率”。
